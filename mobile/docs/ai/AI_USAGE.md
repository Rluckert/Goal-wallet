# AI Usage — mobile/

This document tracks how AI (Claude Code) was governed while building the `mobile/` layer of the `goal-wallet` exam, per the exam's requirement to explain *how* AI use was governed, not just that it was used.

## Skills used in this layer

| Skill | Purpose | Location |
|---|---|---|
| `generate-domain-fixtures` | Generate test fixtures/factories with real edge cases for domain types (`SavingsGoal`, `Money`, `Progress`). | `mobile/.claude/skills/generate-domain-fixtures/` |
| `write-architecture-justification` | Draft the trade-offs/alternatives/scalability justification for architecture and pattern decisions, for the root README. | `mobile/.claude/skills/write-architecture-justification/` |
| `generate-conventional-commit` (shared) | Gate commits on green tests, write Conventional Commits messages, create branches when a new phase starts. | `/.claude/skills/generate-conventional-commit/` |

## Agents used in this layer

| Agent | Purpose | Location |
|---|---|---|
| `ddd-boundary-reviewer` | Reviews `mobile/src` for DDD layering violations, domain purity, named-pattern placement, and coverage against the declared target. | `mobile/.claude/agents/ddd-boundary-reviewer.md` |
| `clean-code-reviewer` (shared) | Reviews for SOLID/DRY adherence and clean-code smells — a separate grading criterion from DDD layering. | `/.claude/agents/clean-code-reviewer.md` |
| `build-test-diagnostician` (shared) | Triages build/test failures and proposes a root cause before any fix is attempted. | `/.claude/agents/build-test-diagnostician.md` |

## What was generated with AI vs. written/adjusted by hand

- **`src/domain/*`** (`Money`, `Progress`, `SavingsGoal`) — AI-generated from the DDD boundary this repo's own scaffolding (`.claude/agents/ddd-boundary-reviewer.md`) already committed to. The over-deposit rule (`DepositExceedsTargetError` instead of silently clamping) was an explicit design call made and justified in the plan before coding, not left to the model to invent ad hoc.
- **`src/domain/__fixtures__/SavingsGoal.fixtures.ts`** — generated with the `generate-domain-fixtures` skill, targeting the specific edge cases that matter for this type's rules (0%, partial, exactly 100%, over-deposit attempt), not a generic boundary set.
- **`src/application/*`, `src/infrastructure/*`, `src/presentation/*`** — AI-generated per the approved plan (`.claude/plans/velvety-humming-lantern.md`), each layer reviewed against the DDD boundary rules and iterated on real test/typecheck failures rather than accepted on first pass (see corrections below).
- **`infrastructure/webview/contracts.ts`** — hand-read `web/src/contract.ts` first and reimplemented the native-side mirror to match exactly (types, field names), rather than generating an independent guess at the shape — the two sides must agree on the wire format even though they're intentionally not imported from each other.
- **`metro.config.js`, `android/local.properties`, `scripts/copy-webapp.js`** — written to fix real failures hit during the actual `npx react-native run-android` verification pass (unresolved `rn-savings-notifier`, missing SDK path, no packaged WebView assets), not written speculatively ahead of time.
- **`infrastructure/nativeLibrary/ConfirmDialog.ts`, `GoalListScreen.tsx`'s rewrite** — AI-generated at the human's explicit direction after reviewing the running app: the native list's `<DepositInput/>` quick-deposit and the WebView's deposit form did the same thing twice, so the list became read-only and a tap now asks a native yes/no (`ConfirmDialog.show`, wrapping `libreria/`'s new `showConfirmDialog`) before navigating to the detail. See `libreria/docs/ai/AI_USAGE.md` for the library-side half of this change.
- **`infrastructure/repositories/AsyncStorageGoalsRepository.ts`, `application/CreateGoal.ts`, `presentation/components/CreateGoalModal.tsx`** — AI-generated at the human's explicit request to close HU4's "deseable" persistence gap and remove the hardcoded-seed-only limitation together. `AsyncStorageGoalsRepository` wraps `InMemoryGoalsRepository` as its cache rather than duplicating the Map lookup logic — reuse over rewrite, once the existing class's shape turned out to fit exactly what a cache-aside layer needed.

## What was rejected or corrected from AI output (critical judgment)

- **Fixture id collision.** The first version of `SavingsGoal.fixtures.ts` had every named preset default to the same id (`'goal-1'`). This silently collapsed multi-goal test seeds (a `Map`-backed fake repository) down to one entry. Caught by `GetGoals.test.ts` actually failing (`expected length 2, received 1`) rather than a code read — fixed by giving each preset a distinct id.
- **Test helper misplaced.** `FakeGoalsRepository.ts` was first placed inside `application/__tests__/`. Jest's default `testMatch` collects *any* file under a `__tests__/` folder as a test suite, so it failed with "must contain at least one test." Moved to `application/__testUtils__/`, a name Jest's default config won't collect.
- **`jest.mock` factory scoping.** Several mock factories (for `rn-savings-notifier`, `react-native-webview`) initially referenced the file's top-level `React` import from inside the factory body. Babel's `jest.mock` hoisting forbids referencing out-of-scope variables and threw a `ReferenceError` at transform time — fixed by `require`-ing `react` locally inside each factory instead.
- **`WebView` ref typing, two attempts.** First attempt: `useRef<WebView>(null)` — wrong, `WebView` is the component's type, not its instance type, and produced a cascade of "type never" errors on every prop. Second attempt: a hand-rolled `interface WebViewRef { postMessage: ... }` — also rejected by `tsc`, because the package's real declared ref type is a full class with many more methods than the one used, and a narrower interface isn't assignable to it. Settled on `useRef<ComponentRef<typeof WebView>>(null)` — the correct utility for extracting a component's real ref type, whatever it turns out to be.
- **Non-memoized selector.** `selectAllGoals` initially did `Object.values(state.goals.goals)` inline, returning a new array reference every call — react-redux warned about this at runtime ("returned a different result... should be memoized"). Not left as noise: rewritten with `createSelector` from Redux Toolkit before moving on.
- **`transformIgnorePatterns`, extend not replace.** When `@reduxjs/toolkit` (via `immer`), `react-redux`, and `react-native-webview`'s ESM builds each broke Jest in turn, the fix was to *append* to the RN preset's own `transformIgnorePatterns` regex, not replace it — replacing it would have silently stopped transforming React Native's own internal packages too.
- **`ddd-boundary-reviewer` run before closing the phase caught a real inconsistency**: `GoalListScreen.tsx` imported `<DepositInput/>` straight from `rn-savings-notifier`, while `notifyGoalCompleted` already went through an `infrastructure/nativeLibrary/SavingsNotifier.ts` wrapper — the boundary rule was applied to one native-library touchpoint and not the other. Fixed by adding `infrastructure/nativeLibrary/DepositInput.ts` (a thin re-export) and importing from there instead.
- **The same review also flagged two things that, on reflection, weren't real defects** — the agent's own rule text was imprecise, not the code:
  - `GoalDetailScreen.tsx` importing the `webViewMessageAdapter` singleton with no interface/port in front of it, unlike the Repository's interface split. Deliberately **not** given an interface: `WebViewMessageAdapter` has exactly one wire format and no plausible second implementation, unlike goal storage (a real future backend swap). Adding a port here would be an abstraction with no payoff, which the project's own conventions explicitly avoid.
  - `GoalListScreen.tsx`/`GoalDetailScreen.tsx` importing `react-native` and `react-native-webview` primitives (`View`, `FlatList`, `<WebView>`) were flagged against the literal "infra-only" import rule — but rendering UI is presentation's actual job. Rather than leave the rule to keep misfiring on this, `mobile/.claude/agents/ddd-boundary-reviewer.md` itself was corrected to distinguish *orchestration* imports (Redux side-effects, the library's imperative calls — infra-only) from *rendering* imports (mounting `<WebView>`/RN components in JSX — presentation's job).
- **Quick-deposit removed on product grounds, not a bug.** The `<DepositInput/>` integration in `GoalListScreen` was working, tested, and had already passed a `ddd-boundary-reviewer` pass — the human caught the redundancy (two deposit paths doing the same thing) by using the running app, not from a code read, and directed the specific replacement (a native confirm dialog gating navigation to the existing WebView flow) rather than leaving the fix open-ended.
- **Coverage gaps closed, not left as noise.** The same review pass surfaced `goalsSlice.ts` at 66.66% branch coverage (the `?? 'Failed to ...'` fallback in both `.rejected` handlers was never hit — Redux Toolkit's own error serialization always fills in a message, e.g. `"Rejected"` for a `null` error, so a naive `.rejected(null, ...)` test doesn't actually exercise the fallback; the tests construct the rejected action then override `error` to omit `message`) and `SavingsNotifier.ts` at 0% function coverage (mocked wholesale in `goalsSlice.test.ts`, so the wrapper's one line — that it actually forwards to `notifyGoalCompleted` — was never itself verified). Both closed with targeted tests rather than accepted as acceptable gaps.
- **First `clean-code-reviewer` pass, and a judgment call on whether to fix its one finding.** DIP/LSP were explicitly re-verified rather than assumed (grepped `application/` for `infrastructure/` imports — zero; checked `InMemoryGoalsRepository`'s return types actually match what `MakeDeposit` assumes). The one real finding — `useThemeColors()` + `useMemo(() => createStyles(colors), [colors])` repeated identically 3× across `GoalListScreen.tsx`/`GoalDetailScreen.tsx` — was borderline against this project's own "three similar lines beats a premature abstraction" convention. Extracted anyway (`useThemedStyles.ts`) specifically because SOLID/DRY is now a named, separately-graded criterion, not because the repetition itself had become a real problem — a values call, not a correctness one, and recorded here as such rather than silently presented as "the code was wrong."
- **A planned test-mocking workaround turned out unnecessary.** The persistence plan assumed `goalsSlice.test.ts` would need an explicit-factory mock for `AsyncStorageGoalsRepository` (the same workaround already required for `rn-savings-notifier`/`react-native-webview`, since automocking a module transitively `require()`s the real thing). In practice, plain automock worked fine — `@react-native-async-storage/async-storage`'s JS entry point doesn't touch `TurboModuleRegistry`/`NativeModules` at import time the way those two do; the only real blocker was an ESM-build transform error, fixed the same way as every prior instance of that exact class of problem. Two other test files (`GoalDetailScreen.test.tsx`, `CreateGoalModal.test.tsx`) genuinely did need a hand-added `AsyncStorage` mock, though — they exercise the real thunk chain end to end (not a mocked repository), caught by running the tests, not by re-reading the plan.
